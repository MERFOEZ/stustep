## 1. ماذا تم تنفيذ في هذه المرحلة؟

**لم يُكتب أي سطر كود، ولم يُعدَّل أي ملف قائم.** ما تم:

1. قراءة **29 ملف Dart** (‏9,324 سطراً) في `lib/` بالكامل
2. استخراج **مخطط قاعدة البيانات الفعلي** من الكود (لا يوجد مستند مخطط في المشروع)
3. تحديد **البنية المعمارية الحقيقية** وليست المفترضة
4. جرد **الخدمات والأنماط البرمجية** القائمة لتقليدها
5. تحديد **نقاط الإدماج الآمنة** و**الملفات المحظورة**
6. رصد **16 نقطة تعارض محتملة** مع الإضافات المستقبلية
7. وضع **خطة تنفيذ من 9 مراحل** واستراتيجية Git

**سبب وجود هذه المرحلة:** الإضافة على مشروع جماعي قائم بلا تحليل مسبق تُنتج تعارضات دمج وتكراراً في المنطق وكسراً لعمل الزملاء. المرحلة 0 هي التي جعلت الرقم النهائي **4 ملفات معدَّلة فقط بـ ~10 أسطر**.

## 2. البنية الحالية للمشروع (Architecture)

### 2.1 حزمة التقنيات الفعلية

| البند | التقنية |
|---|---|
| **الإطار** | Flutter · Dart SDK `^3.10.4` · Material 3 |
| **الباكند** | ❗ **لا يوجد باكند مخصص** — التطبيق يتصل بـ Firebase مباشرة (BaaS) |
| **قاعدة البيانات** | Cloud Firestore `^6.7.1` — مشروع `stustep-4c1ea` |
| **المصادقة** | Firebase Auth `^6.5.4` + Google Sign-In `^7.2.0` |
| **تخزين الملفات** | Cloudinary (رفع Unsigned) · Archive.org لروابط الفيديو |
| **الذكاء الاصطناعي** | OpenRouter / DeepSeek عبر `dio` |
| **التخزين المحلي** | `SharedPreferences` — و`Hive` مُهيَّأ لكنه **غير مستخدم إطلاقاً** |
| **إدارة الحالة** | `setState` (~95%) + `Provider` لعنصر واحد + `StreamBuilder` مباشر |
| **الترجمة** | `easy_localization` — عربي/إنجليزي، الافتراضي `ar`، 136 مفتاحاً متطابقاً |
| **حقن التبعيات** | ❗ `get_it` موجود في `pubspec.yaml` لكنه **لم يُستخدم أبداً** |

### 2.2 نمط المعمارية

**Feature-First Folder Structure** — وليست Clean Architecture ولا MVVM ولا BLoC.

- `lib/core/` → المشترك عبر المشروع (خدمات + ثيم)
- `lib/features/<اسم>/` → كل ميزة في مجلد مستقل
- `lib/shared/widgets/` → الودجت المشتركة (ملف واحد فقط حالياً)

**لا توجد طبقة Repository.** الخدمات تتحدث مع Firestore مباشرة.

### 2.3 تدفق البيانات الحالي — مساران متناقضان

**المسار المنضبط** (الشات والمصادقة):
```
User → Screen → Service (Singleton) → Firestore → Model.fromFirestore() → Screen
```

**المسار المخالف** (الكليات/الأقسام/المواد):
```
User → Screen → FirebaseFirestore.instance مباشرة داخل build() → Map<String,dynamic> خام → Screen
```

| استدعاء Firestore داخل الشاشة | `lib/features/courses/colleges_screen.dart:73` |

## 4. نمط Firestore الحالي

### 4.1 المجموعات القائمة

| Collection | Doc ID | الحقول | من يكتبها |
|---|---|---|---|
| `users` | `uid` | `uid`, `name`, `email`, `createdAt` | `auth_service.dart` |
| `colleges` | تلقائي | `name`, `icon` | ❌ الـ Console يدوياً |
| `departments` | تلقائي | `name`, **`collegeId`** | ❌ يدوياً |
| `courses` | تلقائي | `title`, `cover_image`, **`departmentId`**, `lectures[]` | ❌ يدوياً |
| `groups` | ثابت | `name`, `description`, `category`, `members[]`, `lastMessage`, `lastMessageTime` | `chat_service.dart` |
| `groups/{id}/messages` | تلقائي | 12 حقلاً (نص/مرفق/رد/حالة رفع) | `chat_service.dart` |

### 4.2 العلاقات

```
colleges (doc.id) ──< departments.collegeId ──< courses.departmentId ──> lectures[] (مصفوفة مضمّنة)
users (doc.id = uid) ──< groups.members[]  ·  messages.senderId

⚠️ users غير مرتبط بـ colleges أو departments إطلاقاً
```

### 4.3 القواعد الضمنية المستخرجة

1. **العلاقات بمعرّف نصي مسطّح** (`collegeId`, `departmentId`) — لا `DocumentReference`
2. **شرط `where` واحد + فرز محلي** لتفادي الفهارس المركّبة
3. **إزالة التطبيع مقبولة** (`senderName` داخل الرسالة)
4. **`cover_image`** هو الحقل الوحيد بـ snake_case — شذوذ لا يُقلَّد
5. **لا يوجد `firestore.rules` في المستودع** 🔴 → الأرجح أن القواعد في وضع اختبار مفتوح

### 4.4 التخزين المحلي

| المفتاح | المحتوى | الخطر |
|---|---|---|
| `downloaded_videos_meta` | قائمة الفيديوهات المحمّلة | 🔴 **عالمي، غير مرتبط بـ uid** — تبديل الحساب يُظهر ملفات مستخدم آخر |
| `venc_aes_key_b64` / `venc_aes_iv_b64` | مفتاح AES و IV | 🔴 نص واضح + IV واحد لكل الملفات |
| `theme_mode` | الثيم | ✅ سليم |

## 5. نظام المستخدمين والصلاحيات

### 🔴 النتيجة: لا يوجد نظام صلاحيات إطلاقاً

بحث شامل عن `role` / `admin` / `permission` / `isTeacher` / `dashboard` → **لا وجود لأي منها**. (`'role': 'user'` الموجود خاص برسائل الـ AI ولا علاقة له بالصلاحيات.)

- **نوع مستخدم واحد:** طالب. كل من يسجّل يحصل على نفس الصلاحيات
- **تسجيل الدخول:** Email/Password أو Google → وثيقة في `users/{uid}`
- **لوحة تحكم:** ❌ غير موجودة. البيانات الأكاديمية تُدخَل يدوياً من Firebase Console
- **الانضمام للمجموعات:** تلقائي وإجباري بمجرد الفتح (`group_chat_screen.dart:49`)
- **حذف الرسالة:** تحقق **واجهة فقط** (`isMe`) — الدالة نفسها لا تفحص شيئاً

**الأثر على موديولنا:** أي محتوى يضيفه المستخدم (سكن / نموذج اختبار) يحتاج ملكية وقواعد أمان نبنيها من الصفر.

## 9. القرارات الهندسية

### القرار 1 — مجموعات ظل (Shadow Collections)
- **Decision:** بيانات الدليل والشروط في مجموعات جديدة معرّف وثيقتها = معرّف الأصل (`department_guides/{departmentId}`)، لا حقول جديدة داخل `colleges`/`departments`
- **Reason:** الوثائق القائمة يدخلها الفريق يدوياً من الـ Console ويستخدمها زملاء آخرون. أي إعادة استيراد تمسح حقولنا. القراءة بمعرّف معروف رخيصة ولا تحتاج فهرساً
- **Alternative:** توسيع الوثائق القائمة → مرفوض لخطر فقد البيانات والتصادم مع ملكية الزملاء

### القرار 2 — موديول واحد جامع
- **Decision:** `lib/features/admission/` بخمسة مجلدات فرعية
- **Reason:** نقطة دخول واحدة = سطر واحد يُعدَّل، ونماذج الكلية/القسم تُعرَّف مرة واحدة
- **Alternative:** خمس ميزات منفصلة → خمس نقاط دخول وخمسة تعديلات وتكرار نماذج

### القرار 3 — `admins/{uid}` بدل حقل `role`
- **Decision:** وجود الوثيقة = صلاحية إدارية، تُفحص بـ `exists()` في القواعد
- **Reason:** صفر تعديل على `auth_service.dart` المحظور، وصفر ترحيل للمستخدمين الحاليين
- **Alternative:** حقل `role` في `users` → يتطلب تعديل ملف محظور + ترحيل بيانات

### القرار 4 — Cloudinary خلف `StorageService`
- **Decision:** إعادة استخدام Cloudinary، لكن خلف خدمة جديدة تكرر ~12 سطراً من `chat_service` عمداً
- **Reason:** Firebase Storage يتطلب تفعيل الفوترة. إعادة تصنيع دالة زميلك = تعديل أنشط ملف في المشروع
- **Alternative:** إعادة تصنيع `chat_service.uploadFile` → تعارض دمج مؤكد مقابل 12 سطراً

### القرار 5 — خريطة خارجية
- **Decision:** تخزين `GeoPoint` وفتح تطبيق الخرائط بـ `url_launcher`
- **Reason:** الخريطة المدمجة تتطلب مفتاح API + تعديل `build.gradle` و`Info.plist` = ملفات حساسة وتكلفة
- **Alternative:** `google_maps_flutter` → مؤجَّل لما بعد المناقشة

### القرار 6 — Enum كنص لا كرقم
- **Decision:** `'yemeni_general'` وليس `0`، مع `code` و`fromCode()` وقيمة افتراضية آمنة
- **Reason:** الفهرس الرقمي يتغير عند إضافة قيمة في منتصف الـ enum → تتلف كل البيانات المخزَّنة
- **Alternative:** `index` → أصغر حجماً لكنه هش وغير مقروء في الـ Console

### القرار 7 — تخزين المعدل مع سلّمه
- **Decision:** `gpa` + `gpaScale` يُخزَّنان معاً، والتطبيع لحظة المقارنة فقط
- **Reason:** «3.6» بلا سلّم لا معنى له. تخزين القيمة المطبَّعة يفقد الأصل ويمنع تصحيح جدول التحويل لاحقاً
- **Alternative:** تخزين النسبة المطبَّعة فقط → فقدان معلومات لا رجعة فيه

### القرار 8 — صفر فهارس مركّبة
- **Decision:** شرط `where` واحد + فرز وفلترة في الذاكرة
- **Reason:** مطابق لأسلوب الفريق القائم (`chat_service.dart:53`)، ولا انتظار لبناء فهارس ولا نشر إضافي
- **Alternative:** فهارس مركّبة → أداء أفضل عند آلاف الوثائق، غير مبرر في حجم بيانات المشروع

## 11. استراتيجية Git

> Git يتعارض على **الملف** لا على المجلد. 52 ملفاً جديداً + 10 أسطر معدَّلة = احتمال تعارض شبه معدوم.

| الفرع | ملفاته الحصرية | يعتمد على |
|---|---|---|
| `feat/admission-core` | النماذج · الخدمات · Hub · الترجمات · الربط | — |
| `feat/admission-guide` | `guide/` | core |
| `feat/admission-requirements` | `requirements/` | core |
| `feat/admission-housing` | `housing/` + `pubspec` + `Manifest` | core |
| `feat/admission-exam-papers` | `exam_papers/` | core |
| `feat/admission-matcher` | `matcher/` + الاختبارات | guide + requirements |

**سبعة قوانين إلزامية:**
1. `feat/admission-core` يُدمج أولاً ووحده — بقية الفروع تتفرّع منه **بعد** الدمج
2. مفاتيح الترجمة متداخلة تحت `"admission"` وتُضاف في نهاية الملف
3. **ممنوع `dart format` على أي ملف قائم** — يحوّل 3 أسطر إلى 300 سطر تعارض
4. ملف واحد = مالك واحد
5. `git pull --rebase origin main` يومياً
6. أي تعديل على ملف محظور يوقف المراجعة
7. PR لكل موديول فرعي، لا PR عملاق

## 13. أسئلة المناقشة المتوقعة

**س: لماذا مرحلة تحليل كاملة قبل الكود؟**
لأن المشروع جماعي وقائم بالفعل بـ 9,324 سطراً وأربعة مساهمين. الإضافة بلا تحليل تعني تعارضات دمج وكسر عمل الزملاء. التحليل هو ما جعل التعديل على الكود القائم **4 ملفات و10 أسطر فقط**.

**س: ما البنية المعمارية المستخدمة ولماذا؟**
Feature-First: كل ميزة في مجلد مستقل يضم شاشاتها ونماذجها وودجتها. اخترناها لأنها بنية المشروع الأصلية أولاً، ولأنها تسمح لعدة أعضاء بالعمل بالتوازي على ملفات مختلفة ثانياً.

**س: لماذا Firestore وليس SQL؟**
لأنه قرار المشروع القائم ولا مبرر لتغييره. وهو مناسب هنا: بيانات وثائقية متداخلة، مزامنة لحظية جاهزة (`.snapshots()`)، ومصادقة مدمجة تربط الصلاحيات بالمستخدم مباشرة بلا خادم وسيط.

**س: لماذا لم تعدّل الملفات القائمة لتحسينها؟**
لأن إعادة التصنيع الشامل في مشروع جماعي نشط تُنتج تعارضات ضخمة وتكسر عمل الآخرين. وثّقنا كل ملاحظة كخطر معروف بدل تغييره من طرف واحد. التحسين قرار فريق لا قرار فرد.

**س: كيف تضمن ألا يكسر موديولك التطبيق؟**
بثلاث طبقات: مجموعات Firestore جديدة كلياً (لا تمسّ القائمة)، ملفات جديدة كلياً (لا تعارض)، ونقطة دخول واحدة قابلة للفصل بسطر واحد.

**س: ما أخطر مشكلة اكتشفتها؟**
غياب `firestore.rules` نهائياً — قاعدة البيانات على الأرجح مفتوحة. والأخطر أن نشر قواعد تغطي المجموعات الجديدة فقط سيُغلق المجموعات القائمة ويُعطّل التطبيق عند كل المستخدمين، لذلك أُجّل إلى مرحلة مستقلة مع اختبار في المحاكي.

**س: لماذا فصلت الـ Model عن الـ Service؟**
الـ Model يمثّل شكل البيانات ويحوّل بين Firestore والكائن. الـ Service يمثّل العمليات (قراءة/كتابة/منطق). الفصل يجعل المنطق قابلاً للاختبار بلا اتصال بالشبكة، ويسمح بتغيير مصدر البيانات لاحقاً دون لمس الشاشات.

**س: لماذا تخزّن الـ Enum كنص؟**
لأن التخزين بالرقم يعتمد على ترتيب القيم داخل الـ enum. إضافة قيمة في المنتصف تُزيح كل الأرقام وتتلف البيانات المخزَّنة. النص ثابت ومقروء في الـ Console.

**س: لماذا Cache في الخدمات؟**
شاشة المساعد تحتاج كل الأدلة وكل الشروط معاً. بلا Cache تُقرأ من Firestore في كل مرة — تكلفة وبطء. البيانات شبه ثابتة (تُحدَّث مرة كل عام دراسي)، فالتخزين المؤقت في الذاكرة قرار صحيح.

**س: كيف يعمل التحقق من القبول؟**
الطالب يدخل شهادته (نوع + مسار + معدل + سلّم + سنة تخرج). يُطبَّع المعدل إلى نسبة مئوية موحّدة، ثم تُطبَّق ستة شروط بالتسلسل: نوع الشهادة، المسار، المعدل مقابل الحد الفعلي، صلاحية سنة التخرج، المعادلة، ودرجات المواد المشترطة. النتيجة ثلاث حالات — مؤهل، قريب من الشرط، غير مؤهل — مع **أسباب محددة** لا رفض مبهم.

## 15. إذا سألني الدكتور عن هذه المرحلة أقول

> قبل ما أكتب أي كود، حللت المشروع كله — 29 ملف و9,324 سطر — عشان أعرف كيف يشتغل ومين يملك أي ملف.
>
> طلعت بأربع نتائج:
> **الأولى:** استخرجت شكل قاعدة البيانات من الكود، لأن المشروع ما فيه أي توثيق لها.
> **الثانية:** حددت قائمة ملفات ممنوع ألمسها، لأنها إما شغل زملائي الحالي أو ملفات لو غيّرتها بتكسر بيانات المستخدمين.
> **الثالثة:** لقيت نقطة إدماج جاهزة — بطاقة في الشاشة الرئيسية موجودة أصلاً وما تسوي شي، فأربط موديولي فيها بثلاثة أسطر بس.
> **الرابعة:** رصدت المخاطر، وأخطرها إن المشروع ما فيه قواعد أمان لقاعدة البيانات نهائياً.
>
> والنتيجة إني بضيف حوالي 52 ملف جديد، وما بعدّل غير 4 ملفات بعشرة أسطر — يعني احتمال أكسر شغل الفريق شبه معدوم.
